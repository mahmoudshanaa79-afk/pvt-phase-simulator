# Independent audit: 02_field_units

**Verdict: APPROVED**

## What I independently re-verified (not taken from the builder's report)

**1. The previously blocking finding, C-1 (unit-switch false-staleness), is genuinely fixed.**

- Reproduced the underlying floating-point issue directly against the shipped `units.py`: `373.7993794602593 K → °F → K` returns `373.79937946025933`, not the original value; `4045258.429683001 Pa → bar → Pa` likewise differs at the last bit. The non-exactness the original finding described is real, not hypothetical.
- Read `adapters.py`, `app.py`, and `state.py` in full. `current_inputs` — the value compared for staleness — is built in `app.py` from `session()["temperature_k"]` / `session()["pressure_pa"]` (the canonical SI state) via `TemperatureUnit.KELVIN` / `PressureUnit.PA`, i.e. an identity conversion. It is **not** recomputed each rerun by round-tripping the displayed field value through the currently selected unit — that was the mechanism the original finding described, and it's gone.
- Traced `synchronize_unit_inputs` (`state.py`) through both invocation paths (the `on_change` callback and the unconditional resync call at the top of `_input_form`): the canonical `temperature_k`/`pressure_pa` is updated only when the *displayed field value itself* changed since the last render (`temperature_value != rendered_temperature_value`), never merely because the unit changed. A pure unit switch instead recomputes the displayed value *from* the unchanged canonical K/Pa. Both invocation orders are idempotent with each other.
- Ran the test suite myself rather than trusting the "62 passed" claim: `pytest tests/test_app_adapters.py tests/test_app_sweeps.py tests/test_app_streamlit.py` → **119 passed**, independently reproduced.
- Confirmed `test_non_exact_unit_round_trip_preserves_result_identity` is a real, non-tautological regression test, not a rubber stamp: it uses the exact `373.7993794602593 K` / bar-psi values from the original finding, asserts the naively round-tripped signature *would* differ (`round_tripped.signature != submitted.signature`), then asserts the running app does **not** mark the result stale after that same unit switch, and **does** mark it stale after a genuine `1e-9` edit. This test would fail if the bug were reintroduced — it isn't just checking that no exception was raised.

**2. Unit conversion correctness (`units.py`)**

- MPa = ×1e6, bar = ×1e5, psi = ×6,894.757293168 (exact SI/avoirdupois definition) — verified by direct computation.
- Celsius: `K = °C + 273.15`; Fahrenheit: `K = (°F + 459.67) × 5/9` — standard exact affine forms, no scientific engine relation restated.
- Absolute-zero rejection verified per unit by reasoning about exact IEEE-754 cancellation (`x + (-x) = 0.0` exactly for any finite float `x`), and confirmed against `test_absolute_zero_is_rejected_in_every_temperature_unit`: `0 K`, `-273.15 °C`, `-459.67 °F` all correctly reduce to `0.0 K` and are rejected.

**3. Sweeps and exports thread units correctly, not just cosmetically.**

- `SweepRequest` stores its fixed variable in the request's own recorded field unit; `run_sweep` converts to K/Pa exactly once per point via `validate_scientific_inputs`, matching the "convert once at the boundary" invariant.
- `_validate_axis`'s `require_positive` is correctly gated to pressure only (Celsius/Fahrenheit sweep bounds may legitimately be negative; the K conversion is still checked downstream per point).
- CSV/JSON exports carry both the selected-unit values and canonical `temperature_k`/`pressure_pa`, satisfying "exports state their units explicitly."
- `views.py` sweep-control widget keys are unit-scoped (`sweep_start_{kind}_{units.temperature}_{units.pressure}`), so switching units resets to a correctly-converted default instead of reinterpreting a stale raw number under the new unit.

**4. No scope creep into protected artifacts.**

- `git diff --stat` and `git status --porcelain` against `src/pvt_phase_simulator/`, `data/`, `docs/validation/`, `tests/golden_master/` relative to base `cd908da9` both returned empty — confirmed directly, not taken on faith from the stated hashes.
- No thermodynamic relation appears in the UI layer; `units.py` performs only affine unit conversions.

## Non-blocking observations (safe to defer)

- **D-1** (carried forward): `_presentation_figure`'s hovertemplate substitution (`views.py`) uses a literal `.replace(" K", ...).replace(" Pa", ...)`. Checked the actual templates in the frozen `plotting.py`: every call site forces `pressure_unit=PlotPressureUnit.PA`, so each template contains exactly one `" K"` and one `" Pa"` token today. Safe now; fragile only against a future wording change in that frozen module.
- **D-2** (carried forward): sweep CSV/table values aren't rounded to a unit-appropriate precision (fine for Pa/K, excessive digits for bar/psi/°C). Cosmetic.
- Minor clarity note, not a defect: `app.py`'s `_input_form` calls `validate_scientific_inputs` twice per rerun — once against displayed field values (for a field-unit-aware error message) and once against canonical K/Pa state (for the actual scientific identity). Deliberate and commented; correct but easy to misread on a future edit.

## Conclusion

The blocking finding recorded from the prior audit cycle (`C-1`, false staleness from non-exact unit round-trips) is resolved in this revision, and I verified the fix mechanistically rather than accepting the builder's claim. No new blocking or moderate defects were found. Both carried-forward D-severity items remain accurate and non-blocking.
