## Finding: unit switching frequently causes a false "stale result" (and blocks exports) — contradicts the PR's own documentation

The work package's own updated documentation states: *"Changing a unit converts the editable value and preserves the physical state; it does not run a calculation or make a current scientific result stale"* and *"Unit-only changes therefore redraw existing results without recomputing or changing their scientific identity."*

This is false for a large fraction of real inputs. `result_is_stale` (`state.py:161`) compares `ScientificInputs.signature` — an exact tuple of `(mole_fractions, temperature_k, pressure_pa)` — with `!=`. `current_inputs` is recomputed on *every* rerun by re-parsing whatever is currently sitting in the (possibly unit-converted) text field through `validate_scientific_inputs`. Switching the unit selector round-trips the value through `convert_temperature`/`convert_pressure` and then re-parses it back to SI — and IEEE-754 double arithmetic does not guarantee that round trip returns the bit-identical float it started from.

I verified this directly against the production `validate_scientific_inputs` function (not a hand-built reference), submitting a case and then only switching display units without touching the physical value:

```
submitted = validate_scientific_inputs((50,0,50), 305.7, 12.34)          # via K / MPa
current   = validate_scientific_inputs((50,0,50), t_f, p_psi,            # same case, via °F / psi
              temperature_unit=FAHRENHEIT, pressure_unit=PSI)
```

Across 20,000 random realistic `(temperature_k, pressure_mpa)` pairs, **50.2% of temperature signatures mismatched by 1 ULP after a K→°F→K round trip** (e.g. `373.7993794602593` → `373.79937946025933`), even though the physical state is unchanged. Because `result_is_stale` uses exact equality, this means: for roughly half of arbitrary user inputs, merely clicking the temperature-unit selector to °F — with no other change — will make the UI show *"Stale result — submitted scientific inputs changed. Run this calculation again before use,"* and, per the app's own stale-handling logic, disable the CSV/JSON download buttons until the user needlessly resubmits. This propagates to every cached result type gated the same way (flash, envelope, critical, critical_scan, sweep), since they all key off the same `current_inputs`/signature comparison.

The existing regression test for exactly this behavior, `test_presentation_unit_change_does_not_stale_a_calculated_result` (`tests/test_app_streamlit.py:100`), passes only because it happens to use the suite's canonical default case (300 K / 5 MPa via °C/bar), and I confirmed by direct computation that this specific value round-trips exactly through all four supported units — it is not representative. Tellingly, a *different* test in the same file (`test_field_unit_selection_preserves_state_and_submits_si_to_engine`, line 90) already had to use `pytest.approx(300.0, abs=1e-13)` rather than exact equality for the same 300 K value through Fahrenheit for the *submission* path — i.e. the imprecision was empirically visible to the builder in one place but its consequence for the staleness comparison a few lines away was not connected.

This doesn't corrupt any scientific result (the flash/envelope/critical numbers themselves are still exactly correct once actually computed) and doesn't touch the frozen engine, so it isn't an "A"-level scientific-integrity defect. But it's a real, easily-reproduced functional regression that defeats a central, explicitly documented promise of this specific work package, and will visibly misbehave for ordinary users switching to Fahrenheit. It needs a tolerance-based (or SI-state-retaining, non-round-tripping) staleness comparison before this can be considered done.
