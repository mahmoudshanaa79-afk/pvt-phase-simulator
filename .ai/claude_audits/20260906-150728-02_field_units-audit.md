The sweep-bounds validation is deliberately asymmetric (`require_positive=True` only for pressure, not temperature, since Celsius/Fahrenheit legitimately admit negative field values) — I checked this doesn't let non-physical states slip past validation: temperature-to-K conversion is affine and monotonic, so if both sweep endpoints validate as > 0 K, every interior interpolated point is a convex combination of two positive numbers and is therefore also guaranteed positive. `run_sweep`'s per-point `validate_scientific_inputs` call is outside its `try/except`, which looked suspicious at first (an interior point could theoretically raise unguarded), but the above proves that path is unreachable. Not a defect.

## Genuine defect found

**Certified-critical-point hover tooltips ignore the selected presentation unit.**

`views.py`'s `_presentation_figure()` is the boundary-conversion shim that makes non-native units (°C, °F, psi — none of which the frozen `pvt_phase_simulator/plotting.py` knows about) possible. It converts `trace.x`, `trace.y`, and does a literal string-replace on `trace.hovertemplate`. That's a deliberate, necessary workaround since the frozen plotting module only supports Pa/kPa/MPa/bar for pressure and has no temperature-unit parameter at all.

However, the frozen module's `_add_critical_point()` (used by `plot_phase_envelope`, `plot_criticality_map`, and `plot_critical_solver_path`) builds the "Certified critical point" star marker differently from every other trace: it bakes the fully-formatted hover string — including the numeric Tc/Pc values and their unit suffix — into `trace.text` at figure-construction time via `_critical_hover()`, then references it with a bare `hovertemplate="%{text}<extra></extra>"`. Because the UI always calls these plotting functions with `pressure_unit=PlotPressureUnit.PA` (so it can do its own conversion afterward), that baked text is always in raw K and raw Pa.

`_presentation_figure()` only rewrites `trace.x`, `trace.y`, and `trace.hovertemplate` — it never touches `trace.text`. So:
- The star's on-chart **position** is correct (x/y are numeric data, caught by the conversion loop).
- The star's **hover tooltip** always reads e.g. `T=321.58 K` / `P=8534443.24 Pa`, even when the user has selected °F/psi and every axis label, axis tick, and every other trace's hover on the same chart correctly shows °F/psi.

Reachable in normal use, not just behind an obscure toggle: `render_phase_envelope()` shows this marker by default whenever a certified critical point exists alongside an envelope; `render_critical_point()`'s criticality-map and critical-solver-path charts show it too (the path chart behind a "Show critical solver figures" toggle, the other two not).

I confirmed no test exercises this: the unit-switching tests (`test_field_unit_selection_preserves_state_and_submits_si_to_engine`, `test_presentation_unit_change_does_not_stale_a_calculated_result`, the sweep/export unit tests) all check metrics, exports, and CSV/JSON — none render a phase-envelope or criticality-map figure under a non-K/Pa unit and inspect its `trace.text`/hover content. This gap in coverage is exactly why it went uncaught.

This is squarely inside the declared objective — "Every conversion happens at the application boundary, once, on the way in and on the way out" — and is a real hole in that boundary, not a cosmetic nit. It does not corrupt underlying science, exports (verified: `_display_state`/`_sweep_point_export` correctly carry both presentation and canonical K/Pa values everywhere), or the primary Tc/Pc metric cards (verified correct in `views.py` lines ~742-748). It is contained to one specific marker's mouseover text on three optional chart overlays.

## Other observations (non-blocking)
- The same `_presentation_figure()` hovertemplate rewrite uses a literal `.replace(" K", …).replace(" Pa", …)` substring substitution rather than a structured template rewrite. I checked every hovertemplate string the UI passes through it and found no case where this produces a wrong result today (no incidental `" K"`/`" Pa"` substrings in surrounding text), but it's fragile against future wording changes in the frozen plotting module's hover strings. Worth a code comment or a more robust approach, not urgent.
- `pressure_mpa` is exported redundantly alongside the new `pressure`/`pressure_unit` fields in the current-case JSON; harmless duplication, not a defect.
- Sweep-table pressure rounding (`round(value, 5)`) doesn't adapt precision to the selected unit's magnitude (fine for Pa's large numbers, slightly over-precise for psi/bar); purely cosmetic.

## Verdict rationale
Everything scientific — unit math, boundary-conversion order, absolute-zero rejection in every unit, sweep monotonicity, export completeness (both presentation and canonical values always present), and untouched frozen artifacts — checks out under independent re-derivation. The one real defect is a presentation-layer leak in hover text for a specific overlay marker, contained and fixable without touching the frozen engine or any exported/decision-critical value. That keeps this out of NOT_APPROVED territory but it is a genuine violation of the work package's own stated invariant, so it should not pass silently either.
