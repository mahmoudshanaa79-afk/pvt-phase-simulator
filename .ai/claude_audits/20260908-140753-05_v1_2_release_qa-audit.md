## Genuine finding: `_termination_failed()` substring classification is not "correct for all known members" as claimed

The builder's own recorded safe-defer note (workflow_state.json, D-4) says the substring check `any(word in status for word in ("failed", "failure", "lost"))` is "currently correct for all known enum members." I checked the actual `EnvelopeTerminationReason` enum (`phase_envelope.py:69-79`): 8 members, of which `CORRECTOR_FAILED`, `BRANCH_LOST`, `NUMERICAL_FAILURE` match the substrings, but `MINIMUM_STEP_REACHED` does not — despite its own message text being *"Minimum temperature step reached **without an acceptable correction**"* (`phase_envelope.py:1200`), which is semantically a non-convergence failure, not a benign stopping condition like `TARGET_REACHED`/`MAXIMUM_POINTS`. So the claim that the classifier is correct for all known members is itself inaccurate — it silently under-classifies at least one real failure mode.

**Impact is limited, not blocking:** the raw `termination_status` and `termination_message` strings are *always* rendered verbatim in the report table regardless of `_termination_failed()`'s verdict (`reports.py:382-383`), so no fabricated or hidden data results — a reader inspecting the branch table still sees the true reason. The only effect is that a `MINIMUM_STEP_REACHED` branch with zero accepted points gets labeled "Unavailable" (grey) instead of "Failed" (red) if it has no points, which is a cosmetic under-statement of severity, not a truthfulness violation of the "never fabricate/hide a failure" invariant. This confirms the D-4 entry as legitimate but slightly mis-described; I'm restating it more precisely rather than treating it as new.

## Genuine finding: transient failure message doesn't reach the Overview body on the failing run

Tracing `run_app()`'s execution order: `begin_result_attempt(session(), "flash")` clears the prior result *before* `page.run()`, but `store_result_action_failure(...)` (which populates the specific failure message `_show_action_failure` reads) only runs *after* `page.run()` has already executed and rendered Overview. Since there's no `st.rerun()` on the failure path (only on success), the Overview page body renders the generic "Submit valid fluid inputs..." info message on the run where the failure actually occurs — the specific `FLASH_ACTION_FAILURE` text only appears in the sidebar status block that same run, and only shows up in the Overview body on the *next* rerun.

I confirmed the new regression test (`test_unexpected_flash_retry_has_no_traceback_or_obsolete_result`) does not actually catch this: it asserts `any(failure in item.value for item in app.error)`, which is satisfied by the sidebar's `st.error(...)` alone — it never checks that the Overview body's own message reflects the failure on that same pass. This is a real gap between what the test verifies and what the code actually does, though the substantive requirements (no traceback, no obsolete result shown) are still genuinely met — the sidebar error is plainly visible to the user in the same interaction, and no false/stale data is ever displayed. This is a minor UX/polish inconsistency, not a truthfulness or safety defect.
